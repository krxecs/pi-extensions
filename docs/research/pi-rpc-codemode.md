# Pi RPC children and codemode workflows

Research for [Verify Pi RPC and codemode extension constraints](https://github.com/krxecs/pi-extensions/issues/4), under [Specify a compatible multi-agent Pi extension](https://github.com/krxecs/pi-extensions/issues/2). Checked against the first-party `@earendil-works/pi-coding-agent` **v1.5.2** documentation and source ([tag](https://github.com/earendil-works/pi/tree/v1.5.2/packages/coding-agent), [package manifest](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/package.json)). This is a feasibility note, not an extension implementation or a guarantee about other Pi releases.

## Answer in brief

**Verified:** An extension can launch a separate `pi --mode rpc` process using ordinary host-side Node process APIs, then drive that child over JSONL (or use the exported Node `RpcClient`). The child has its **own** session, resources, extension runtime, model selection and tools. RPC offers prompt/steer/follow-up/abort, state and session operations, and an event stream; prompt acceptance is not completion. The CLI loads the built-in `codemode` extension, but its tool is initially inactive: enable it with `--tools +codemode` or `defaultTools: ["+codemode"]`. Scripts call other tools in a QuickJS sandbox; there is no RPC command for directly executing a codemode script. [RPC overview](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc.md), [RPC command union](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-types.ts), [SDK session ownership](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/sdk.md#session-lifecycle), [codemode registration](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/extensions/codemode/index.ts), [enablement](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md#enable-codemode).

**Architectural limit:** “Codemode is the sole script runner” is feasible as a *policy for model-authored tool scripts*, not a documented deterministic host API for executing a saved JavaScript workflow. A command or prompt can start a model turn *asking* it to use codemode, but cannot submit raw script source to codemode over RPC. A command context does not expose `executeTool()`, and the codemode tool declares `model-only` exposure (not callable as a nested tool); the script is authored by the model in its tool call. An extension may define a codemode-callable helper tool for workflow operations, but this does not change who invokes the script. [RPC commands](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md), [command/tool contexts](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/core/extensions/types.ts), [codemode tool definition](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/extensions/codemode/tool.ts), [tool exposure](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#tool-exposure).

## Child lifecycle and observation

- **Start and configuration.** `pi --mode rpc` is a long-lived child; normal CLI switches configure provider/model, working directory, tools, extensions and session storage. A Node/Bun extension can spawn it through the host runtime; Pi's `RpcClient` already spawns a Node CLI, correlates command responses, and supplies `onEvent`, `prompt`, `abort`, session methods and `promptAndWait`. Its default `cliPath` is `dist/cli.js`, relative to its spawning `cwd`; for an installed or rebranded CLI, supply a verified runnable path or implement the JSONL protocol yourself. The checked repository example uses a built CLI path. [RPC launch](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc.md#start-rpc-mode), [client source](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-client.ts), [example](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/examples/rpc-client.ts).
- **Protocol and completion.** Each LF-delimited command can carry an `id`; correlate responses by ID, not arrival order. Consume stdout continuously with a strict LF splitter (Node `readline` also splits Unicode separators), respect stream backpressure and use stderr only for diagnostics. `prompt` responds with `started`, `queued` or `handled`; `handled` need not start a run. Subscribe before prompting. `agent_end` only closes a low-level run; `agent_settled` closes automatic retries, compaction recovery and queued continuations. Even `agent_settled` is not proof of task success: inspect `message_end`'s final assistant stop reason, tool errors, `aborted`, and command/child-process failures. [RPC framing/lifecycle/errors](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc.md), [prompt disposition](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md#prompt), [event contract](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/json.md#event-sequence), [message types](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/message-types.md).
- **Steering and cancellation.** While streaming, a new `prompt` needs `streamingBehavior: "steer" | "followUp"`; separate `steer`, `follow_up`, `clear_queue`, `abort` and `abort_retry` commands exist. Steering is delivered after the current assistant turn and its tool calls; follow-up waits until the agent finishes. `abort` waits for idle, but queued messages can continue; use `clear_queue` first if stopping all queued work. Treat abort as cooperative and implement host deadlines/process-exit handling. Closing stdin or SIGTERM initiates orderly shutdown; after a grace period a supervisor may kill an unresponsive child. [prompting/abort/queue](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md#prompting), [RPC shutdown](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc.md#shutdown), [client stop implementation](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-client.ts).
- **Streaming detail.** `message_update` carries text/thinking/tool-call deltas rather than cumulative messages; use `contentIndex`, replace blocks at `*_end`, and take `message_end.message` as authoritative. Tool start/update/end events carry `toolCallId`; nested codemode tool calls have `parentToolCallId`, execute through validation and `tool_call`/`tool_result` hooks, and are not separate transcript messages. A direct RPC `bash` call has `bash_execution_update` records with its request ID, unlike generic session events. [JSON event reference](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/json.md), [nested tool contract](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#calling-other-tools).

## Context, interfaces and isolation

- **Startup resources.** The child discovers its own extensions, trusted project resources, prompt templates, skills, context files and settings in its working directory; CLI switches (`--tools`, `--extension`, `--no-extensions`, `--session-dir`, `--session`) shape it. A session's working directory governs tool paths and project context. To give a child a restricted capability set, configure its CLI tools/resources and explicitly verify what loaded; merely using `codemode.mode: "only"` hides active tool declarations from the model but leaves the tools callable by scripts, and `--tools` has separate MCP exposure behavior. `--no-extensions` also disables built-in extensions unless explicitly reloaded, so do not assume codemode remains available. [CLI options](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md#tools), [settings](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/settings.md#tools), [sessions/cwd](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/sessions.md#continue-or-switch-sessions), [SDK resource behavior](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/sdk.md#configuring-a-session).
- **Cross-extension APIs.** Within one session runtime, `pi.events.on/emit` is a shared event bus; an extension can register TypeBox-schema tools, commands, and a namespaced `codemode`-exposed tool (callable while registered). `pi.getAllTools()` and `pi.getCommands()` expose discovery metadata. These are in-process interfaces, **not RPC commands**; there is no documented bridge for firing a parent's event bus into a child or submitting arbitrary extension tool calls over RPC. A child can load the same extension and execute a named `/command` via RPC `prompt`, or let its model call an exposed tool; wire any cross-process event transport explicitly. [event bus example](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/examples/extensions/event-bus.ts), [extension APIs](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#pievents), [tool exposure](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#tool-exposure), [RPC command union](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-types.ts).
- **RPC extension UI.** A child extension sees `ctx.mode === "rpc"` and `ctx.hasUI === true`: dialogs need the host to send an `extension_ui_response` keyed by request ID; notifications/status/widgets can be ignored. Terminal `custom()` and several TUI methods are unavailable or degraded. The first-party `RpcClient` publicly types its listener as session events and has no method for sending UI responses; a UI-dependent child needs a raw protocol client or separately verified adapter. Avoid blocking unattended workers on dialogs. [RPC UI protocol](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-extension-ui.md), [RpcClient source](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-client.ts), [raw client example](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/examples/rpc-extension-ui.ts).

## Codemode as workflow substrate

- **Availability and discovery.** The CLI's built-in codemode extension is enabled by default as an extension, but the `codemode` tool is registered **inactive**; activate it with `--tools +codemode`, `defaultTools: ["+codemode"]`, or `pi.setActiveTools()`. `codemode.mode: "only"` changes presentation, not permission/isolation. In *SDK-created* sessions, built-in factories are not loaded automatically; add `createCodemodeExtension()` to `DefaultResourceLoader` and bind extensions. Scripts can find callable tools via `ALL_TOOLS`, `searchTools`, `describeTool` and `describeNamespace`; `direct` tools must be active to be callable, while registered `codemode`/`deferred` tools remain callable without being active. Scripts cannot call `codemode` recursively. [CLI enablement](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/cli.md#enable-codemode), [SDK setup](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/sdk.md#codemode-mcp), [extension tool exposure](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#tool-exposure), [codemode guide](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/codemode.md).
- **Sandbox/limits.** Script input is raw JS in an async QuickJS function (optional first-line `// @options`), not a general Node runtime: no Node, filesystem, network or timers, except capabilities reached through tools and non-chat `models` classifiers/image generation. Scripts can await/batch tool calls; only explicit `text()`, `image()`, `console` or return output reaches the model. Failures keep partial output and **do not roll back** already-run tool calls; pending unawaited calls are canceled when the script exits. Limits include 256 MB VM memory, 16,777,216 output characters, 100,000 output calls, 262,144 JSON characters per store value / 1,048,576 aggregate, and two codemode workers per Pi process by default (configurable by `PI_CODEMODE_MAX_WORKERS`); a script waiting for a worker fails after 60 seconds or its earlier deadline. Script timeout covers queue wait. [codemode scripts/globals/store/limits](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/codemode.md).
- **Persistence versus replay.** Successful `store()` writes append branch-local `codemode-store` custom entries, so `load()` sees them after session resume on that branch. This is bounded JSON state, **not** a saved program counter or automatic replay of a pending script. Other extension state can be stored via `pi.appendEntry()` (not model context), in tool-result `details`, or as a `custom_message` (model context); rebuild from the active branch after `session_start`/`session_tree`. Session files are append-only trees, with compaction affecting model context rather than deleting raw history; `get_entries(since)` provides a durable entry cursor and `get_tree` gives branch structure. `--no-session` cannot resume after exit. These primitives support an application-owned checkpoint protocol, not exactly-once step execution after a crash. [codemode store](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/codemode.md#store-values), [extension persistence](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#persist-state), [session format](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/session-format.md), [RPC entries](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md#get_entries), [session storage](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/sessions.md#control-session-storage).
- **Launch surface.** `pi.registerCommand("workflow", {handler})` can parse arguments and call `pi.sendUserMessage()` to ask the model to run a codemode workflow; an RPC client sends `/workflow ...` with `prompt`, whose `handled` disposition covers the command, **not** any independent work it starts. A `.md` prompt template can instead expand `/workflow ...` into model instructions, with substitutions and arguments. Both need the agent to choose a codemode call; neither forces a supplied raw script to execute. `get_commands` discovers extension commands, templates and skills but excludes built-in TUI-only commands. [command/input lifecycle](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#understand-the-lifecycle), [registerCommand/sendUserMessage](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#piregistercommandname-options), [prompt templates](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/prompt-templates.md), [RPC prompt/commands](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md#discoverable-commands).

## Specification implications (proposals, **not** SDK guarantees)

1. **Choose the meaning of “workflow.”** If model-directed scripts suffice, a `/workflow` command or prompt template can inject the workflow goal and require the model to use codemode; verify by observing the `codemode` tool call and its result, and fail explicitly if it did not run. If saved scripts must execute deterministically without model mediation, the public RPC/codemode contract does not supply that route; specify a separate runner or an upstream Pi API change instead of promising parity. [RPC command union](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/modes/rpc/rpc-types.ts), [codemode definition](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/src/extensions/codemode/tool.ts).
2. **Own orchestration state outside the sandbox.** Give each child a durable session path and app-owned child/workflow ID, record step intent and completion with idempotency keys, and reconcile against `get_entries(since)` plus active-branch state on restart. Mark uncertain side effects for manual reconciliation rather than blindly replaying them; `store()` commits only on successful script completion, while earlier external tool effects are not undone. [RPC entries](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md#get_entries), [codemode failure/store semantics](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/codemode.md).
3. **Define cross-process compatibility deliberately.** Preserve the documented in-process `pi.events` and extension-author tools/commands where practical; add an explicit, versioned parent/child transport if the same events must cross RPC processes. Probe Pi features at startup (`get_commands`, tool metadata via a child extension if needed), pin and test an exact Pi version, and decide how an unattended child handles dialogs and permissions. These are design choices, not built-in cross-process guarantees. [event bus](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/extensions.md#pievents), [RPC command surface](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-commands.md), [RPC UI](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/rpc-extension-ui.md).

**Version boundary:** All precise commands, field names and limits above are verified for tag `v1.5.2`; the checked sources do not establish the first release that introduced each capability or compatibility with a different Pi distribution. Pin a tested Pi release and run a protocol smoke test (codemode present/active, extension command dispatch, stream/settle, resume, cancellation and UI behavior) before making a minimum-version claim.
